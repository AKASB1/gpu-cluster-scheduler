# Benchmark

Every number produced here is **simulated, with assumed parameters** (docs/simulator.md). It says how policies compare *in this simulation, under these assumptions*; it says nothing about production schedulers or real clusters.

## How to reproduce

From the repository root, with Go and the Python environment of the README active:

```bash
go run ./cmd/benchmark -tune     # tuning on the tuning seeds only -> configs/tuned/tuned.json (committed)
go run ./cmd/benchmark -tune-add # tune only scenarios added later; frozen entries stay unchanged
go run ./cmd/benchmark           # full evaluation with the frozen tuning -> benchmarks/results/benchmark/ + docs/figures/
go run ./cmd/benchmark -quick    # smoke subset (about 1 minute) -> benchmarks/outputs/quick/ (ignored)
```

The evaluation refuses to run when the experiment configuration changed after tuning (its SHA-256 is stored in `configs/tuned/tuned.json`). Traces, per-run JSON, and policy logs go to the ignored `benchmarks/outputs/`. `benchmarks/results/benchmark/manifest.json` records the commit, the configuration hash, the commit of the frozen tuning, the seeds, the Go, Python, SciPy, and HiGHS versions, the hardware class, and a note on the machine load. Decision and solve times are machine-dependent values (`wall_` columns, `wall.csv`, `wall_decision_cost.csv`): solver calls report wall-clock and process CPU time, and the decision-cost microbenchmark runs every case five times (`-count 5`) and reports the minimum, the median, and the maximum. They depend on the machine and its load and are never used in a comparison.

S13 needs the Helios trace, which is not committed: run `bash scripts/fetch_helios.sh` (or `powershell -ExecutionPolicy Bypass -File scripts/fetch_helios.ps1`) first, which downloads it into the ignored `benchmarks/outputs/helios/` and checks its SHA-256. Without it the benchmark skips S13 and lists it under `skipped_scenarios` in the manifest.

## Protocol

- **Configuration.** `configs/experiments/benchmark.json` (generated by `scripts/make_experiment.py`, the JSON is the source of truth): scenarios, policies, seeds, objective weights, tuning budget. Clusters in `configs/clusters/`, workloads in `configs/workloads/`, scenario overrides as JSON merge patches.
- **Offered load** is the requested work per second (`runtime_s * gpus * workers`, in reference-GPU-seconds) divided by the capacity of the cluster in speed-weighted GPUs (sum of GPUs x class speed). The generator calibrates the arrival rate per seed on that seed's user population (docs/simulator.md §10). Gang and topology constraints make the usable capacity lower, so a nominal 0.95 can already saturate a policy that blocks at the head of its queue.
- **Seeds.** Tuning seeds 1001–1005 and evaluation seeds 1–20 are disjoint. S9, S11, S13, the capacity sweep, and the sensitivity variants use seeds 1–10; S8 uses 50 instances per set (instance seeds 1–50). A trace depends only on the scenario's workload and the seed, never on the policies (common random numbers; tested).
- **Objective** (tuning and summary score): `J = P95(bsld)/R_s + P95(wait)/R_w + (1 - goodput) + SLO violation rate + (1 - Jain)` with all weights 1 (a term is 0 where it does not apply, and J_waste has weight 0 in `s15-fail-ckpt-none`, see "Interpretation"). The J-term check (`go run ./cmd/benchmark -jterm-check`, result in `configs/tuned/jterm_check.csv`) runs every policy on the tuning seeds and compares each term's spread across policies with its seed-to-seed noise; see "Interpretation" for the terms it found uninformative and what was done. `R_s`, `R_w` are the means of `fifo+first_fit+none` on the tuning seeds of the same scenario, recorded in `configs/tuned/tuned.json`. J is the summary score; every metric is reported.
- **Tuning** (`-tune`, tuning seeds only). (1) References `R_s`, `R_w` per scenario. (2) Default parts on S1 at load 0.80, one dimension at a time: the placement (with `fifo` and no backfilling), then the backfill (with that placement; the oracle is excluded), then the order; the comparison experiments vary one part around these defaults (`{order}`, `{placement}`, `{backfill}` in the configuration). (3) Every parameterized policy in every scenario gets the same budget: 8 configurations (its defaults plus 7 random draws from a fixed search stream, seed 7) on the 5 tuning seeds; the lowest mean J wins. Search spaces: `aging_per_hour` U[0, 4]; `history` 1–5; preemption `min_gap` 1–7 and `max_victims` {1, 2, 4, 8, 16}; `milp_rolling` `k` 4–24, `h` 8–48, `slot_s` {120, 300, 600, 900}, `mip_rel_gap` {0.01, 0.05} (an exact gap of 0 is not an online option: it made single runs take tens of minutes); `risk` `quantile` U[0.5, 0.99]; `scenario_milp` `k` 4–12, `h` 6–24, `slot_s` {300, 600, 900}, `scenarios` {4, 8, 12}, `lambda` {0, 0.25, 0.5, 1}, `alpha` {0.8, 0.9, 0.95}, `mip_rel_gap` {0.01, 0.05}. The result is committed before the first evaluation run and never re-tuned after. Tier 2 scenarios were added later and tuned with `-tune-add` on the same seeds and budget, which tunes only scenarios without an entry and leaves every frozen entry and the default parts unchanged; their entries were committed before their first evaluation. Distribution-shift scenarios (`tuned_from`) have no tuning of their own: they reuse the parameters of their base scenario. A full re-run of `-tune` on the final commit (29 minutes, into a separate file) reproduced the default parts, all references, and all chosen parameters; the search scores of a few `milp_rolling` configurations in S9 and S11 differed (their solves have a wall-clock safety limit), without changing any choice.
- **Statistics.** Mean and 95% Student-t interval across seeds; paired differences against `fifo+first_fit+none` on common seeds with t intervals; win/tie/loss counts per seed (tie: relative difference at most 1e-9).
- **Checks on every run.** The invariants (no over-allocation, gangs, classes, preemptibility, ordering, retained work) and the accounting identities (Little's law as an identity, allocated GPU-seconds, waste decomposition) are checked on every simulated run; a violation aborts the benchmark. On every S8 small instance, the MILP plan is replayed in the simulator and must reproduce the optimum, and no policy may beat the MILP reference.

## Interpretation

- Every result is from the simulator (docs/simulator.md), whose model leaves out network contention between jobs, model-dependent speeds, and correlated failures, and whose parameters are assumptions.
- The synthetic workload's distributions are assumptions shaped after qualitative findings of public trace studies, not fitted to any trace. S13 replays real submissions, sizes, and run times, but its estimates are synthetic and its cluster is derived, so it is "replayed jobs on a simulated cluster", not a reproduction of the Helios cluster.
- The pool-model reference of S8 medium is a lower bound, so its gaps over-state the true gaps.
- Wall-clock and CPU values come from a shared workstation and are indicative only.
- **J in S13.** The references `R_s`, `R_w` come from `fifo+first_fit+none`, which in the partitioned replay cluster blocks every virtual cluster behind the head job of one (P95 wait 177 h on the tuning window). Every other policy's slowdown and wait terms are then near 0, and J reduces to one minus Jain's index over the per-VC mean slowdown, which is low under backfilling because one overloaded VC keeps a backlog while the others empty. J therefore ranks the baseline above every EASY variant although EASY cuts the P95 wait from 22.4 h to 0.08-0.17 h. Read S13 by its wait and slowdown columns.
- **J-term check.** `configs/tuned/jterm_check.csv` (every policy on the tuning seeds; spread of the per-policy means against the mean seed-to-seed standard deviation): 138 of 145 (scenario, term) pairs are informative. J_waste in `s2-95-exact` and J_wait in S6 (`s6-ckpt-none/short/long`) are not. The check was first run on the parameter configurations of the tuned policies only, misread as "all informative", and the Tier 1 evaluation ran with all weights 1; those weights were not changed afterwards (the tuning was frozen and the results seen), so in S2-95-exact and S6 J carries a term that adds seed noise. In the Tier 2 scenarios, evaluated after the corrected check, the one uninformative term (J_waste in `s15-fail-ckpt-none`) has weight 0 (`zero_weights`); the check before that change is `configs/tuned/jterm_check_before_s15_weight.csv`, and J of `s15-fail-ckpt-none` is therefore not comparable with the J of the other S15 scenarios. In S13, J_waste and J_slo are identically 0.
- **Capacity sweep.** Sizes are for finite 2000-job traces: a cluster below the offered work can meet the P95 target over a trace while its backlog grows, so they are not steady-state capacities.
- **Shift variants** (`s10-shift-*`, `s11-shift`) use the parameters tuned on their base scenario on purpose (a model fitted on one error regime, evaluated on a worse one); their results include the effect of that mismatch.
